## Legend

- **Shape mínimo**: Estrutura JSON mínima necessária para identificar o store. Blobs/ArrayBuffer são referenciados pelo tamanho/tipo, não incluídos inline.
- **Copy+reconcile**: Exportar dados do legado, importar no novo schema, reconciliar diferenças (chaves em duplicata, campos faltando).
- **Copy+idempotência**: Garantir que IDs chaves sejam únicas no novo sistema; preservar contadores e correlation IDs para dedup.
- **Copy+blobs**: Preservar binários (fotos, PDFs) como ArrayBuffer ou Blob objects; não converter ou compressar sem validação explícita.

## Migration Principles (immutable)

1. **Idempotência total**: Uma migration pode ser executada N vezes sem criar duplicatas. Use `idempotency_key` ou `queueId` como marker.
2. **Não atribuir tenant/user por inferência**: Se o contexto (tenant_id, user_id) não puder ser provado a partir dos dados, preserve o legado em vez de atribuir valores arbitrários.
3. **Preservar UUID/idempotency keys**: Nunca regerar IDs. Os UUIDs originais devem migrar intactos.
4. **Preservar blobs/fotos**: Blobs e fichas fotográficas devem ser migrados como-is. Qualquer transformação requer validação binária posterior.
5. **Nenhuma exclusão antes de confirmação da cópia + reconciliação**: A regra de ouro: faça backup, valide, **depois** apagar. Nenhum dado legado é excluído até que o novo store confirme gravação bem-sucedida de 100% dos registros.
6. **Marker por versão/user/tenant/device**: Cada migration carrega um marker `v1`, `v2`, etc. por versão do schema, e opcionalmente `userId`/`tenantId`/`deviceId` para migrations específicas por contexto.
7. **Preservar legado quando contexto não puder ser provado**: Se não for possível determinar de qual tenant/user/device os dados vêm, mantenha-os no legado com flag `origin: "unknown"` em vez de apagar.
8. **Exportação emergencial de pendências continua disponível**: Até que o OFFLINE READY seja declarado, o backup em `localStorage.pending_backup` e a fila `syncQueue` devem permanecer intactos e restauráveis.
