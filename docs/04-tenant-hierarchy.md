# Tenant‑>Fazenda‑>Retiro‑>Pasto hierarchy

## Overview
The domain model used by the Web‑front is built around a strict hierarchical identifier chain:

```
tenant (user account) → fazenda → retiro → pasto
```

* **tenant** – conceptually the logged‑in user's *account*.  
* **fazenda** – a property/farm that belongs to a tenant.  
* **retiro** – a sub‑unit of a fazenda (e.g., a herd or grazing sector).  
* **pasto** – the smallest tactical unit (a pasture plot) that lives under a retiro.

Every record that participates in the domain flow carries a **stable foreign‑key** that points to its parent in the chain:

| Table   | Parent column(s)                     | Meaning                              |
|--------|--------------------------------------|--------------------------------------|
| `fazendas`      | `user_id` (via tenant)               | Owner of the farm. All other tables reference `fazenda_id`. |
| `retiros`       | `fazenda_id`                         | A sub‑division of the farm.          |
| `pastos`        | `retiro_id` (and also stores `fazenda_id` for denormalisation) | A pasture plot. |
| `lancamentos`   | `pasto_id`, `retiro_id`, `fazenda_id` | Moves / consumptions that are tied to a concrete pasture. |
| `syncvet_*` etc. | Various foreign keys that ultimately trace back to `pastos.fazenda_id`. | Cross‑domain services resolve the tenant → farm → retiro → pasture path to enforce permissions and to compute balances. |

### Why the hierarchy matters
* **Routing** – URLs reflect the path: `/admin/fazendas/:fazendaId/retiros/:retiroId/pastos/:pastoId`.  
* **Guards** – All navigation through `RoleRedirect` checks the user’s *role data* (`roleData.fazendaId`) against the target *fazenda* to enforce that a user can only see what belongs to their assigned farm.  
* **Authorization** – Guardrails (`useGuardrails`) compare the user’s session timestamp with the `updated_at` of the target record; the hierarchy guarantees a single chain of IDs to verify.  
* **Realtime channels** – Channels are scoped by `fazenda_id` or `retiro_id`, so a channel name like `operacoes-capataz-{fazendaId}` automatically isolates data per farm.  
* **Offline sync** – When the app is offline, the local cache stores `retiroId` and `pastoId` locally; on reconnect the sync logic resolves the full chain via those IDs, never via a temporary “global” identifier.  

### Stabilised IDs
All IDs are generated by Supabase using UUIDv13 (client‑side) and are **never re‑used**. The mapping is:

```
user (Account) → hasOne → fazenda (id)
fazenda → hasMany → retiro (id)
retiro → hasMany → pasto (id)
```

Because IDs are immutable and never re‑assigned, a user can always trace the exact lineage of any record without risking collisions or ambiguities.

### Documentation checklist
* **Diagram** – keep an up‑to‑date **ASCII** or **Mermaid** diagram in `docs/` showing the flow.  
* **Permission matrix** – a short table mapping each role (`administrador`, `gerente`, `capataz`, …) to the allowed ancestor levels (e.g., `gerente` may only read farms where `roleData.fazendaId` matches).  
* **API contract** – list all tables that accept `fazenda_id` or `retiro_id` as a write‑parameter.  
* **Guardrails** – reference the `useGuardrail*` helpers that use `updated_at` checks per table; they rely on the hierarchy to guarantee no concurrent write race.  

### Current state
* The frontend already contains the **routing hierarchy** (`/admin/fazendas/:fazendaId/...`).  
* All components that need to traverse up the chain use the same selector pattern (`{ table }.eq('parent_id', parentId)`).  
* Tests for the hierarchy have been added (see `src/test/pages/PastoDetailPage.test.tsx`).  
* The next step is to **document** the diagram and **add a regression test** that asserts a component renders only when the correct ancestor IDs are present.
